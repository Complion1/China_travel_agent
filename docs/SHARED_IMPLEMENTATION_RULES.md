## 1. 开工前

1. 读取 00、当前模块权威规范、当前模块 `_vibe_coding.md` 执行契约、本文件和实施状态。
2. 每份新模块实施提示词在写入前，必须以 [`IMPLEMENTATION_ROADMAP.md`](IMPLEMENTATION_ROADMAP.md) 的 `depends_on` 为唯一依赖真源，确认并展开当前模块的全部直接依赖；不得另建依赖索引、机器可读导航、上下文包或生成器。
3. 对每个直接依赖，实施提示词必须列出要读取的精确权威设计文件及章节。章节选择只覆盖当前任务实际消费、修改或依赖的公共导出、DTO/Protocol、所有权边界、版本/迁移规则和 acceptance gate；写提示词前逐个验证文件引用存在。
4. 不要求无差别读取所有较小编号模块。只有当前模块直接消费、修改或依赖某个上游公共合同时，才把该上游权威设计的上述章节纳入必读范围。
5. 任一引用缺失、直接依赖的公共合同或 acceptance gate 冲突，或任务需要修改已冻结上游设计时，立即停止，报告文件、章节、冲突和最小变更范围，并请求用户授权。
6. 核验分支、HEAD、dirty worktree、目标文件和当前测试入口。
7. 重新验证交接事实，不以 archive、旧报告或过时测试数字作为真值。
8. 只在全部直接依赖的公共合同和 acceptance gate 满足后开始。
9. 如发现跨仓需求或白名单不足，停止并报告证据与最小扩展范围。

## 2. 文档职责

- 模块规范拥有公共合同、业务不变量和验收语义。
- `_vibe_coding.md` 面向能力较弱的编码模型，必须明确目标、文件白名单、精确符号、算法顺序、逐阶段任务、测试矩阵、停止条件和报告模板，不能把关键步骤留给模型自行推导。
- 允许为防止跑偏而重复关键字段、错误映射和伪代码；重复部分必须标注其模块规范来源，并由审查或自动检查保证同步。Prompt 的完整文本优先引用受 hash 保护的资源；确需逐字嵌入时必须验证与资源一致。
- Prompt 资源本身是文本真源；模块规范记录版本、hash 和行为边界。
- 状态文档只保存特定验证快照。

## 3. 代码和工作区

- 使用现有工作区，不创建独立 worktree，除非用户明确要求。
- 保留用户已有修改，不使用 `reset --hard`、`checkout --`、`clean` 或等价破坏操作。
- 只修改任务白名单内文件；白名单不足时先停止。
- 不因测试失败删除功能、放宽合同或扩大模块职责。
- 未经明确授权不创建 commit、不 push、不建 PR、不部署。

### 3.1 分支策略

- 本地 `main` 是稳定集成分支，不直接承载日常功能开发。
- 每个新功能开始前必须从最新本地 `main` 创建独立分支，名称固定使用 `feature/<short-kebab-name>`。
- 一个功能分支只承载一个明确功能及其必要测试、文档；不得顺带混入无关重构。
- 功能验收通过后才能合并回本地 `main`；合并、commit、push 和 PR 仍需服从用户当次授权。
- 修复尚未合并的功能时继续使用该功能分支；已合并功能的新需求创建新的 `feature/` 分支。

## 4. 测试

- 先定向测试，再模块完整测试，再全项目回归，最后才执行真实外部资格。
- 禁止通过删除测试、`skip`、`xfail`、自动 rerun、只跑绿灯子集或放宽断言获得通过。
- `collected 0 items`、覆盖率写入失败和命令非零退出都算失败。
- 模块合同测试默认使用 fake；只有该模块拥有的外部边界可以在单独 live 资格中访问真实服务。
- live 结果必须区分正式资格和诊断重放。失败后不得循环重跑直到偶然全绿。
- 外部供应商的统计可靠性不能由一次 live 资格推断。

## 5. 隐私与安全

- Secret 不进入 Prompt、日志、异常、报告、测试快照或版本库。
- 不记录用户敏感原文、模型原始响应、reasoning、MCP/供应商原始 payload。
- 只输出安全 code、case ID、计数、类型和不可恢复原文的结构标志。
- 真实 API 测试必须得到用户授权；调用次数和正式/诊断性质写入报告。

## 6. Docker 与其他项目

- Docker 资源使用本项目命名空间，执行前核验目标名称。
- 不停止、删除或复用其他项目的容器、网络、镜像、卷和数据库。
- `process_simulation-platform-dev` 明确不属于本项目。

## 7. 通用 `MODULE-CLOSEOUT`

### 7.1 适用条件与阶段合同

- 每个生产 Component 的首次实现或生产代码 maintenance，只有在代码、定向测试、模块测试、覆盖率和当前任务适用的 Docker Gate 全部通过后，才可进入 `MODULE-CLOSEOUT`；完成 closeout 前不得报告最终 `COMPLETE` 或“准备合并”。
- `requalification_only` 和纯设计文档任务不因执行本规则而自动修改说明文档；只有生产实现、生产包、用户命令、测试证据或 Docker 行为的真实状态发生变化时才同步。
- 每份生产实施提示词必须为 closeout 写明前置条件、精确文件白名单、验证矩阵、`STOP`/`NOT_RUN` 条件和最终报告字段。closeout 文件必须显式列入该阶段白名单，不得借收尾修改其他设计、代码或配置。

### 7.2 必查文件与事实边界

1. `README.md`：只同步真实完成模块、当前生产包、用户可执行命令、Docker 说明和经实际命令证明的测试事实。
2. `docs/IMPLEMENTATION_STATUS.md`：只记录特定分支、HEAD 和日期上的真实验证快照，包括精确命令、测试数、覆盖率、Docker 结果和已知限制；它不是设计真源。
3. `Dockerfile`：逐模块检查 `COPY`、依赖安装、runtime 默认 `CMD`/import self-check 和 test target 是否覆盖本次新增或变化的生产包。若无需修改，最终报告必须引用当前 `COPY`、`CMD` 或对应 target 的具体内容，说明为何本次变更已被覆盖；禁止只写 `N/A` 或“无需修改”。
4. 已冻结的模块权威设计和 `_vibe_coding.md` 执行契约不得为迁就代码或测试结果而在 closeout 中修改。发现实现与冻结设计真实冲突时必须停止，列出冲突条款并取得用户批准。

### 7.3 同步后验证与提交边界

- closeout 同步完成后，必须从当前源码重新构建当前任务适用的 runtime/test Docker 镜像，并至少重跑 runtime 默认 `CMD`、受影响模块 Gate 和项目当前要求的完整离线回归。closeout 可能改变镜像构建输入、默认自检或最终交付事实，只有同步后的镜像和回归才能证明最终交付物；同步前的结果不能替代该证明。
- 宿主机 Python 结果不能替代当前模块执行契约或阶段提示词明确要求的 Docker 验收。
- 实施模型不得 stage 或 commit。独立审查通过后，仍须取得用户新的明确授权才可提交；push、PR 和 deploy 继续服从用户当次授权。
- closeout 未完成、同步事实无法由命令证明、同步后重建或回归失败、存在白名单外异常文件时，不得报告 `COMPLETE`；对应阶段必须写 `FAIL`，未进入的后续项写 `NOT_RUN` 并注明被哪个前置条件阻断。

## 8. 停止条件

出现以下任一情况必须停止：

- 需要改变 00 或模块规范已经冻结的语义。
- 需要修改白名单外文件或另一个仓库。
- 需要增加模型调用预算、降低安全门槛或泄漏原始内容。
- dirty worktree 与目标文件存在无法安全合并的冲突。
- 离线门禁未通过却准备执行 live 或进入下游模块。
- 外部服务、余额、鉴权或网络使正式资格无法完成。

## 9. 最终报告

至少包含：

- 分支、开始/结束 HEAD 和 dirty worktree 处理。
- 修改文件及白名单外异常。
- 规范对照和有意偏离。
- 定向、模块、全量、覆盖率、Docker 和 live 命令及结果。
- `MODULE-CLOSEOUT` 的 README/状态页同步、Dockerfile 精确影响证据，以及同步后镜像重建、runtime 默认 `CMD`、受影响模块 Gate 和完整离线回归结果。
- 正式资格与诊断的区别。
- Secret/原始内容泄漏检查。
- staged、commit、push、PR、部署状态。
- 完成、未完成或阻塞结论及剩余风险。
